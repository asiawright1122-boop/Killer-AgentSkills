## MCP 認証は接続できることより安全に運用できることが重要

MCP サーバーの認証設定では、まず接続成功を目標にしがちですが、本当に重要なのは運用を続けても破綻しない構成にすることです。API キー、短期トークン、OAuth など方式はいくつかありますが、選ぶ基準は実装の簡単さだけではありません。権限の粒度、更新のしやすさ、漏えい時の影響範囲まで含めて決める必要があります。

## 認証方式ごとの考え方

### API キー
導入が簡単で、小規模な内部利用や検証用途では扱いやすい方式です。ただし、キーの配布先が増えるほど管理が難しくなります。長期間使い回すと、漏えい時の影響が大きくなる点にも注意が必要です。

### トークンベース認証
有効期限を短くできるため、恒久的な鍵を配るより安全に設計しやすい方式です。発行、更新、失効の仕組みを整えておけば、運用中の事故に強くなります。

### OAuth
ユーザー単位の権限や外部サービス連携が必要な場合に向いています。実装負荷は上がりますが、認可の流れを分離しやすく、複数システムにまたがる環境では管理しやすい選択肢です。

## 導入前の確認事項

認証方式を決める前に、次の点を整理しておくと無理のない構成にしやすくなります。

- 誰が MCP サーバーを利用するのか
- ツールごとに権限を分ける必要があるか
- 人が使うのか、システム同士で使うのか
- トークン失効や鍵ローテーションをどの頻度で行うか
- 監査ログとして何を残す必要があるか

## 安全な設定で押さえるポイント

### 最小権限にする
すべての利用者やクライアントに同じ権限を与える設計は避けたほうが安全です。読み取り専用と更新系を分けるだけでも、誤操作や侵害時の影響をかなり抑えられます。

### シークレットをコードに置かない
認証情報はリポジトリや設定サンプルに直接書かず、環境変数や専用のシークレット管理機構で扱います。ローカル検証用の値と本番値を分離しておくことも重要です。

### 失効とローテーションを前提にする
漏えいしない前提ではなく、漏えいしても被害を限定できる前提で設計します。短命な資格情報、更新手順の標準化、古いキーの迅速な無効化が重要です。

## 認証まわりの切り分け手順

接続エラーが起きたときは、次の順で確認すると原因を特定しやすくなります。

1. 資格情報が期限切れになっていないか
2. クライアントが正しいヘッダーやトークン形式で送っているか
3. サーバー側で必要なスコープや権限が不足していないか
4. 認証成功後に認可で落ちていないか
5. 監査ログに拒否理由が残っているか

認証と認可を同時に扱うと見落としやすいため、どこで拒否されたのかを明確に分けて記録することが大切です。

## 運用で見る指標

安全に運用できているかを判断するには、接続成功率だけでは不十分です。次の指標を継続的に見ると、異常を早く検知できます。

- 認証失敗の件数と急増タイミング
- 無効トークンや期限切れトークンの比率
- 権限不足による拒否回数
- キーやトークンのローテーション実施状況
- 利用者別、ツール別のアクセス傾向

## まとめ

MCP の認証設定では、単に接続できることより、権限設計、シークレット管理、失効運用まで含めて考えることが重要です。小規模な構成では API キーでも始められますが、利用者や接続先が増えるほど、短命トークンや OAuth のような運用しやすい方式が有利になります。
