## まずは症状を分けて考える

MCP サーバーが動かないときは、設定、起動、通信、認証、上流サービスのどこで止まっているかを分けて考えるだけで、調査時間を大きく減らせます。原因を特定する前に設定を何度も書き換えると、かえって問題が見えにくくなるため、切り分けの順番を決めて確認するのが近道です。

## よくある症状の分類

### サーバーが起動しない
実行コマンドの誤り、依存関係不足、環境変数未設定、実行権限不足が代表的です。まずはサーバープロセス自体が正常に立ち上がっているかを確認します。

### クライアントから接続できない
サーバーは起動していても、ソケットやポート、標準入出力の扱い、起動方法の違いで接続できないことがあります。設定ファイルのパス違いも見落としやすい原因です。

### 接続できるがツール呼び出しで失敗する
この場合は、認証情報、リクエスト形式、外部 API の障害、権限不足などが疑われます。MCP の接続成功と、実際のツール実行成功は別問題として扱うほうが整理しやすくなります。

## 切り分け手順

### 1. 起動確認
サーバー単体で起動し、初期化時にエラーが出ていないかを確認します。ここで失敗するなら、MCP クライアントの前にローカル実行環境を見直すべきです。

### 2. 設定確認
クライアント側の設定ファイルにあるコマンド、引数、環境変数、作業ディレクトリが正しいかを確認します。設定のコピー時に古いパスが残っているケースはよくあります。

### 3. 通信確認
接続方式に応じて、標準入出力、HTTP、ソケットのどこで詰まっているかを見ます。タイムアウトならネットワークや待機時間、即時失敗なら設定不整合の可能性が高いです。

### 4. 認証確認
外部サービスと連携するツールなら、トークン期限切れ、API キーの誤り、必要スコープ不足を確認します。認証成功後に認可で落ちることもあるため、ログは細かく見たほうが確実です。

### 5. 上流依存の確認
MCP サーバー自身ではなく、その先の API やデータベースが失敗していることもあります。サーバーの問題か、依存先の問題かを分けるだけで対応方針が変わります。

## 典型的な詰まりどころ

- 依存パッケージは入っているが実行時バージョンが合っていない
- ローカルでは動くがクライアント経由だと環境変数が渡っていない
- 認証情報は正しいが権限スコープが不足している
- サーバー応答はあるが、ツール名や引数形式が期待とずれている
- 外部 API の応答遅延でタイムアウトしている

## 再発防止のために整えたいこと

トラブルを一度解消しても、再発防止の仕組みがなければ同じ問題を繰り返します。最低限、次の点を整えておくと運用が楽になります。

- 起動時に必須環境変数を検証する
- 認証エラーと通信エラーを別のログとして残す
- 外部 API 失敗時のメッセージを具体的にする
- 設定サンプルをチームで統一する
- 変更後に最小構成で接続確認する手順を決める

## まとめ

MCP サーバーの不具合は、接続できないこと自体より、原因が複数層にまたがることが難しさの本質です。起動、設定、通信、認証、上流依存の順に切り分ければ、無駄な試行錯誤を減らせます。問題が再現したときに同じ順番で確認できるよう、確認項目を定型化しておくと運用しやすくなります。
