## 本番運用では便利さより被害を広げない設計が重要

MCP サーバーのセキュリティを考えるときは、単に外部公開を防ぐだけでは不十分です。AI クライアントは便利な反面、広い権限を持つツールを自然言語経由で呼び出せるため、入力の曖昧さや想定外の操作がそのままリスクになります。本番環境では、侵入を防ぐことに加えて、誤操作や権限逸脱が起きても被害を最小化できる設計が重要です。

## 守るべき領域

### 入力の安全性
自然言語入力やツール引数は、そのまま信用しない前提が必要です。入力検証を省くと、意図しないコマンド実行、過剰な検索、危険な更新処理につながる可能性があります。形式チェックだけでなく、許可する操作範囲を明確に絞ることが重要です。

### 認証と認可
接続できることと、実行してよいことは別です。MCP サーバーでは、利用者やクライアントを識別する認証に加えて、どのツールをどの条件で実行できるかという認可設計が欠かせません。読み取りと更新を分けるだけでも、リスクは大きく下げられます。

### ネットワーク境界
すべてのサーバーを直接公開する必要はありません。社内プロキシ、VPN、IP 制限、ゼロトラスト構成などを使い、到達できる主体を減らすだけでも防御効果があります。

## 運用で実施したい対策

### 最小権限の徹底
一つの認証情報ですべてのツールを使える設計は避けるべきです。用途ごとに資格情報を分け、不要な権限を持たせないことが、漏えいや誤操作への最も基本的な対策になります。

### レート制限と使用量制御
MCP サーバーは高頻度で呼び出される可能性があるため、レート制限を設けておくと負荷集中や悪用を防ぎやすくなります。トークンごと、IP ごと、ツールごとの制限を分けて考えると効果的です。

### 監査ログの整備
誰が、いつ、どのツールを、どの結果で呼び出したかを追えるようにしておくと、事故後の調査がしやすくなります。成功ログだけでなく、拒否や失敗も残しておくことが重要です。

### シークレット管理
API キーや内部接続情報をコードや設定例に埋め込まないようにし、専用のシークレット管理機構で扱います。ローテーションのしやすさも含めて設計しておくと、運用負荷を減らせます。

## 見落としやすいリスク

- 読み取り専用だと思っていたツールが副作用を持っている
- ログに機密情報や個人情報がそのまま残っている
- テスト用の資格情報が本番で有効なまま残っている
- 外部 API の権限が広すぎて MCP 側の制御を超えてしまう
- 運用者向けの緊急回避手順がなく、異常時に止められない

## 継続的に見る指標

本番運用では、設定完了時点の安全性だけでなく、変化を監視することが大切です。次の指標を継続的に見ておくと、問題の兆候を早く捉えられます。

- 認証失敗や権限拒否の増加
- 特定ツールへの呼び出し集中
- 深夜や休日など通常と異なる時間帯のアクセス
- 大量取得や連続失敗など不自然な利用パターン
- 監査ログ欠損やログ遅延の発生

## まとめ

MCP サーバーのセキュリティは、単一の設定で完成するものではありません。入力検証、認可、ネットワーク制御、監査ログ、シークレット管理を組み合わせて、被害を限定できる運用にすることが重要です。本番環境では、便利に使えること以上に、安全に止められること、追跡できることを重視すると安定した運用につながります。
