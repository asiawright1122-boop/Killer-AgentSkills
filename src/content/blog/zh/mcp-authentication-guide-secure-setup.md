了解如何正确为您的 MCP 服务器配置身份验证。本指南涵盖 API 密钥、OAuth、基于令牌的身份验证以及保护 AI 代理集成的最佳实践。

## 简介

MCP 服务器一旦接入真实业务，身份验证就不只是“拦一下未登录请求”这么简单。它还决定了模型能代表谁访问什么资源、哪些工具可以被调用、失败时如何定位、密钥泄露后如何止损，以及不同客户端之间如何保持一致的安全边界。

很多安全问题不是出在加密算法不够强，而是出在边界设计过于模糊：共享同一个长期密钥、把用户身份和服务身份混在一起、或者没有给工具调用建立最小权限模型。要把 MCP 用到生产环境，先把这些基础问题想清楚，比单纯接上认证中间件更重要。

## 身份边界：先回答“谁在调用”

为 MCP 设计认证前，建议先区分三种身份：

- **终端用户身份**：模型代表某个真实用户访问资源
- **客户端身份**：IDE、桌面应用或代理运行器本身的身份
- **服务身份**：MCP server 调用下游系统时使用的机器身份

如果这三类身份没有拆开，后续就容易出现权限过大、审计困难和问题难以追溯的情况。尤其是在企业场景里，最常见的错误就是让所有请求都共用一个 server 级密钥，看起来省事，实际上等于放弃了最细粒度的控制能力。

## 常见认证方式：适合什么场景

### API Key：适合内部、轻量、快速接入

API Key 的优点是实现简单，适合内部工具、单一团队或早期 PoC。只要你能保证密钥发放、轮换和撤销流程清晰，它可以支撑不少实际场景。

但它的缺点也很明显：无法天然表达用户级身份，权限粒度通常比较粗，而且一旦泄露，影响范围往往较大。对于面向多租户或需要细粒度审计的场景，不建议把 API Key 当成最终方案。

### OAuth：适合代表用户访问资源

如果 MCP server 需要读取用户自己的文档、代码仓库、工单系统或企业 SaaS 数据，OAuth 通常更合适。它的优势在于可以明确用户授权范围，也更便于撤销、续期和审计。

代价是实现更复杂，尤其要处理重定向、令牌刷新、作用域设计和失效恢复。对不少团队来说，真正的难点不是把 OAuth 接通，而是把失败路径做完整。

### 短期令牌：适合控制风险暴露面

无论底层是 API Key 还是 OAuth，最后都建议尽量让 MCP server 使用短期令牌来承接请求。这样可以降低凭证长期暴露的风险，也更容易对异常会话进行快速失效处理。

## 设计原则：认证不该脱离授权单独存在

很多文章把身份验证和权限控制分开讲，但在 MCP 场景里，两者必须一起设计。因为模型会调用工具，而工具背后往往连接数据库、文件系统、知识库和第三方服务。你不能只验证“请求来自谁”，还要验证“这个身份现在能调用哪个工具、能读写哪些对象”。

至少应明确三层限制：

- 哪个客户端可以连接到这个 MCP server
- 哪类身份可以看到哪些工具
- 某个工具在执行时可访问哪些具体资源

如果只有第一层，没有后两层，就很容易出现“已经登录，但权限过大”的问题。

## 安全配置要点

### 最小权限

每个 token、每个工具、每个下游凭证都应该只保留当前任务所需权限。不要为了省配置时间，把读写权限、管理权限和调试权限打包给同一类调用者。

### 密钥隔离

开发、测试、生产环境必须使用不同凭证；不同租户、不同客户端或高风险工具也应尽量分开。隔离做得越早，出问题时的影响面就越容易控制。

### 过期与轮换

长期不轮换的凭证是最危险的隐患之一。为 API Key 和服务凭证建立明确的轮换周期，为短期 token 设计续期机制，并准备好紧急撤销流程。

### 审计日志

至少要记录认证方式、调用主体、请求时间、工具名称、结果状态和失败原因。不要只记“访问成功/失败”，那样出了问题几乎无法回放真实上下文。

## 落地顺序：先稳住基础，再做高级能力

对多数团队来说，比较稳妥的实施顺序是：

1. 先确定身份边界和权限模型
2. 再选择合适的认证方式
3. 把密钥存储、轮换和日志补齐
4. 最后再做单点登录、多租户隔离、细粒度策略等增强能力

如果一开始就堆高级特性，而基础的 token 生命周期、失败处理和权限收敛没做好，系统很容易变得又复杂又不安全。

## 容易被忽略的失败场景

身份验证方案设计得再完整，也要提前考虑失败时怎么退场。下面几类问题最常见：

- access token 过期后，客户端是否能平滑刷新
- 下游授权范围变化后，工具是否会返回可解释的错误
- 某个用户被禁用后，现有会话多久失效
- 服务凭证泄露后，能否快速只撤销一部分调用链

这些问题平时不显眼，但往往决定生产环境是否真的可控。

## 生产环境建议

如果你的 MCP server 已经要对接真实用户和企业系统，建议至少做到以下几点：

- 对外请求使用短期凭证或可撤销令牌
- 工具权限按功能拆分，不共享超级凭证
- 把认证日志与审计日志打通
- 对敏感工具增加额外确认或策略校验
- 定期验证轮换、吊销和异常告警是否真的可用

## 总结

MCP 身份验证的重点，不是单选 API Key、OAuth 还是 token，而是先把身份边界、权限模型和凭证生命周期设计清楚。认证只是入口，真正决定系统是否安全的是：谁能调用、能调用什么、出了问题能否快速定位并收敛影响。

如果你把 MCP 看作长期基础设施，就应该把认证当成一套持续治理机制，而不是上线前临时补的一层门锁。
