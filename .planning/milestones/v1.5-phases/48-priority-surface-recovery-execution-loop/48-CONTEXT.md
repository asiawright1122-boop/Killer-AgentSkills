# Phase 48: priority-surface-recovery-execution-loop - Context

**Gathered:** 2026-04-09
**Status:** Ready for planning
**Source:** planned Phase `47` diagnosis board, current recovery blockers, and the need to restart traffic with measured public-surface interventions

<domain>
## Phase Boundary

This phase converts ranked recovery opportunities into a measured execution loop on the public surfaces most likely to win traffic back.

This phase covers:

- turning the top recovery opportunities into an execution queue
- defining concrete metadata, content-refresh, and internal-link interventions
- tracking outcomes and operator notes for each recovery action
- preserving crawl, provider, and planning guardrails while interventions ship

This phase does not cover:

- opening new acquisition channels before recovery proof stabilizes
- large-scale redesigns or architecture changes
- expanding paid AI or backup-provider usage
  </domain>

<decisions>
## Implementation Decisions

- **D-01:** Recovery execution should begin with the highest-confidence surfaces, not a broad speculative rewrite.
- **D-02:** Each intervention should have one measurable reason and one tracked outcome note.
- **D-03:** Execution should remain compatible with the current SEO guardrails and recovery board rather than becoming a parallel growth workflow.
  </decisions>

<specifics>
## Specific Ideas

- Candidate intervention classes likely include metadata tightening, content refreshes, internal-link improvements, and canonical clarification on surfaces that still lag.
- The execution queue should be small enough to learn from, but explicit enough that the next growth milestone can scale proven moves instead of guessing.
- This phase should establish the first repeatable business-recovery loop, not just another diagnostic artifact.
  </specifics>
